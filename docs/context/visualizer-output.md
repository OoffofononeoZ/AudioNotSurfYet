# Visualizer 输出质量与可用性

owner 随后通过 [DEC-080](decision-registry.md#dec-080--录制档位按时间对齐先行开放--2026-10-17) 授权：先尝试缓解首录问题；掉帧不破坏时间对齐时可先开放，明确保留流畅度限制。当前开放状态如下；下方首批测量保留原始失败结论，后续多标记验证见文末。

2026-10-17 按 owner 批准的计划核对当前工程输出设置。分辨率与帧率已经进入真实录制链路，无需另建导出通路：Project V3 → RecordingSession → DPR 1 的同一 Canvas → `captureStream(frameRate)` → MediaRecorder。录制结束恢复预览尺寸，沿用 pre-Gain 音轨、取消、命令锁与资源释放。

| 输出 | 实际尺寸 | 视频目标码率 | 当前可用性 |
| --- | --- | --- | --- |
| 720p30 | 1280×720 | 6 Mbps | 默认可用；保留首录掉帧警告 |
| 720p60 | 1280×720 | 9 Mbps | Edge 首录复测有累计偏移，继续禁用 |
| 1080p30 | 1920×1080 | 10 Mbps | Edge 有实际时间偏移，继续禁用 |
| 1080p60 | 1920×1080 | 16 Mbps | 按时间对齐先行开放；保留掉帧警告 |

音频目标码率为 192 kbps；优先 VP9/Opus，已有 VP8/Opus MIME 选择顺序不变。码率是编码器目标值，实际文件大小随内容变化；帧率设置是采集请求，不能据此认定文件已达到质量门槛。

`recordingPresets.ts` 的可用性表供底栏与录制预检共同读取；函数名使用 `isVisualizerRecordingPresetAvailable`，不再把先行开放称作“可靠”。当前可用组合为 720p30 和 1080p60；分辨率菜单明确标注对应 30/60fps，用户选择分辨率时一次性应用该组合，帧率菜单禁用不支持的组合。已导入或恢复的 720p60/1080p30 原样保留并明确提示音画偏移，预检在获取 transport/tap/capture/recorder 前返回 `preset-unavailable`，不自动降档；只有用户明确选择菜单中的另一组合时才变更输出。开放档位均显示简短的首次录制掉帧提示，码率和采集/播放/资源生命周期不变。

## 本轮实测

环境为真实 Chrome **155.0.8059.80**、Edge **155.0.4283.45**，串行执行。四档各录制受控同步片与本地无元数据四秒音乐片，共 16 份；同步片使用 3 秒现有音频，在 1.5–1.55 秒显示白色闪帧。本地音乐不加入 fixture，不记录原文件信息。后续同步片在角落加入已有旋转元素，中心同步区域不变。

所有 16 份都实际使用所选尺寸、采集请求与码率，含一个 VP9 视频流和一个 Opus 音频流，在页面音量 0 时仍有声，FFmpeg 完整解码通过。首批 A/V 事件差最大 28ms、结尾差最大 56ms、相对源时长差最大 203ms，均在既有 100ms/250ms 门槛内。8 份音乐片的实际包帧率及最大帧间隔通过，后续 6 份同步片也通过。

**首批 720p30 同步片失败**：Chrome/Edge 分别约 25.45/27.65fps，最大视频包间隔 500/268ms。失败样本保留，不改判为 unavailable。独立浏览器首录复测在各档均复现；代表性同步片结果如下，均未达到实际包帧率 ±5% 和最多四个目标帧间隔的既有门槛：

| 档位 | Chrome 实际 fps / 最大间隔 | Edge 实际 fps / 最大间隔 |
| --- | --- | --- |
| 720p30 | 25.27 / 500ms | 27.65 / 266ms |
| 720p60 | 47.30 / 634ms | 52.01 / 417ms |
| 1080p30 | 23.93 / 633ms | 26.65 / 366ms |
| 1080p60 | 45.29 / 754ms | 48.89 / 550ms |

诊断中视觉 RAF 没有对应停顿，主线程没有对应长任务；加入持续运动、先截图呈现预览、提前一秒获取采集流均未解决。问题发生于采集/编码输出侧，具体浏览器内部原因尚未确定。无效的等待实验已撤回，生产录制顺序不变。DEC-080 授权前，三个可选档位因此继续排除，720p30 保留历史已接受的默认能力。**首录稳定性缺口至今未关闭**；先行开放不等于严格 fps/间隔门槛通过，没有改写 V5/V6 历史证据或生成整体 readiness。

## 复现与验证

- `tests/e2e/visualizer-output.spec.ts`：真实输出参数、录制锁/释放、页面静音音轨、导入/草稿不降档与早期拒绝。
- 默认仅测正式可用档位；可设置 `VISUALIZER_MUSIC_FILE` 指向本地 ≤8 秒片段，`VISUALIZER_OUTPUT_RUN` 指定独立 run ID。
- 候选矩阵设置 `VISUALIZER_RECORDING_TRIAL=1`。测试仅在自身 localhost 模块响应中放开静态可用性表，生产代码没有旁路；文件标记 candidate trial。失败测量保持失败，不因恢复正式门禁而改判。
- `node tests/scripts/verify-visualizer-output.mjs <run-id> --all` 要求完整 16 份矩阵；不加 `--all` 可检查子集，但每个档位仍需 Chrome/Edge × 同步/音乐四份才可汇总通过。
- 验证器以实际 packet PTS 计算平均 fps，不使用有时为 1000/1 的 WebM 名义帧率；同时检查包顺序、最大间隔、结构、尺寸、时长、音轨、同步和实际解码。

原始媒体、浏览器/采集元数据、RAF/长任务诊断和测量 JSON 仅留在忽略目录 `artifacts/visualizer-composition/output/`。`trial-1` 保存首批矩阵；`cold-60`、`cold-1080-30`、`cold-1080-60`、`preview-check` 等独立样本保留上述复现。短片结果不代表长曲性能或原生 OS 保存人工验收。

代码交付验证：类型检查、6 项录制单元测试、13 项工具测试、生产构建与仓库/文档检查通过。Chrome/Edge 共 4 项正式界面专项通过（禁用选项、导入/草稿/导出保留、预检前拒绝与手动恢复）；测试专用候选响应另在两端生成 1080p60 样本，证明正式代码无旁路。浏览器“成功生成文件”与媒体稳定性结论分别记录，不能混为全部通过。

## 多标记时间对齐验证

后续试验了在现有 RAF 中补充 `requestFrame()`，以及关闭自动采集后手动请求帧。前者仍有 400–600ms 空档且叠加了采集帧率，后者 Chrome 仍有 468ms 空档；均未解决问题，实验代码已撤回，没有把预热、额外 RAF 或手动采集引入生产。手动采集依据 [W3C canvas capture 机制](https://www.w3.org/TR/mediacapture-fromelement/#html-canvas-element-media-capture-extensions)，它能请求帧，但不保证编码器的输出节奏。

新增本地生成的 12 秒同步片，在歌曲 0.15、1.5、6、10.5 秒分别安排 50ms 白色闪帧与音频 burst，检查首录空档前后、后半段及结尾。四档 × Chrome/Edge × 同步/音乐仍为 16 份；`alignment-trial` 保存该矩阵。`--allow-frame-drops` 只把 fps ±5% 和四个目标间隔不达标保留为警告；尺寸/结构、有效递增 PTS、音轨、音画事件 100ms、累计偏移变化 100ms、A/V 结尾 100ms、源时长差 250ms 及完整解码仍是硬失败。默认命令保留严格规则，两种政策写入不同的测量文件，不覆盖旧证据。

| 档位 | 多标记矩阵的时间对齐 | 后续动作 |
| --- | --- | --- |
| 720p30 | 两浏览器通过；首录仍有间隔警告 | 保留默认并标记掉帧 |
| 720p60 | 两浏览器通过 | 满足先行开放条件 |
| 1080p30 | Chrome 通过；Edge 存在真实时间偏移 | 保留限制，不能按“只掉帧”处理 |
| 1080p60 | 两浏览器通过；Edge 有间隔警告 | 满足先行开放条件，标记掉帧 |

上表是 `alignment-trial` 矩阵结论；后续正式门禁的独立首录进一步收紧了 720p60，最终状态以文首表格为准。

通过的样本中，最大音画事件差 37ms、跨标记偏移变化 33ms、A/V 结尾差 29ms、源时长差 32ms；16 项媒体生成浏览器测试和 2 项 Edge 独立复测均完成，生成成功不代替上述逐文件质量结论。16 项工具测试与文档/仓库检查通过。

Edge 1080p30 的画面标记实际落在 0.168、1.601、6.435、11.034 秒，后段相对对应音频峰值约落后 400–499ms，视频末尾约 12.733 秒；不是单纯少几个帧。独立首录两次复测仍失败。测试采样到音频时钟相对录制墙钟累计落后约 454–872ms，歌曲时间跟随该音频时钟；底层时钟失配原因尚未解决。样本位于 `alignment-clock`，均保留失败，不因 owner 接受掉帧而豁免。

新增工具测试覆盖按 PTS 判定对齐、缺失/静音标记、整体位移与累计漂移。该验证限于本地 12 秒片段和当前浏览器，不保证长曲、所有设备或掉帧窗口内的每个动画细节都被保留。

## 正式门禁首录与当前开放

`alignment-production` 不使用候选模块响应，Chrome/Edge 各完成 1080p60 的 12 秒同步片和音乐片。首录实际约 56.74/58.00fps，最大间隔 668/416ms，仍不满足严格流畅度门槛；时间对齐通过：最大事件差 36ms、跨标记偏移变化 17ms、A/V 结尾差 24ms、源时长差 27ms。依 DEC-080 开放 1080p60，并保留提示。

`alignment-720-production` 的 Chrome 720p60 通过，但 Edge 最后一个画面标记在 10.632 秒、对应音频峰值在 10.535 秒，事件差约 97ms；结合前面标记，偏移变化约 134ms，超过累计对齐预算，且画面相对歌曲标记晚 132ms。因此 720p60 仍禁用，不能以“只差一点”或候选矩阵曾通过替代正式复测。检测器会保留晚到标记的实际时间用于漂移计算，避免把超预算标记丢弃后低估漂移；原始媒体和失败结果继续保留。
