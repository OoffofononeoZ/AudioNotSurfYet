# Visualizer 输出质量与可用性

2026-10-17 按 owner 批准的计划核对当前工程输出设置。分辨率与帧率已经进入真实录制链路，无需另建导出通路：Project V3 → RecordingSession → DPR 1 的同一 Canvas → `captureStream(frameRate)` → MediaRecorder。录制结束恢复预览尺寸，沿用 pre-Gain 音轨、取消、命令锁与资源释放。

| 输出 | 实际尺寸 | 视频目标码率 | 当前可用性 |
| --- | --- | --- | --- |
| 720p30 | 1280×720 | 6 Mbps | 保留既有默认；本次发现首录风险，见下文 |
| 720p60 | 1280×720 | 9 Mbps | 未通过稳定性复测，不开放 |
| 1080p30 | 1920×1080 | 10 Mbps | 未通过稳定性复测，不开放 |
| 1080p60 | 1920×1080 | 16 Mbps | 未通过稳定性复测，不开放 |

音频目标码率为 192 kbps；优先 VP9/Opus，已有 VP8/Opus MIME 选择顺序不变。码率是编码器目标值，实际文件大小随内容变化；帧率设置是采集请求，不能据此认定文件已达到质量门槛。

`recordingPresets.ts` 的可用性表供底栏与录制预检共同读取。没有可用组合的分辨率/帧率选项显示“暂不可用”并禁用；已导入或恢复的设置保留并明确提示，预检在获取 transport/tap/capture/recorder 前返回 `preset-unavailable`，不自动降档。每个维度仍允许选择任何有可用组合的值，使用户能手动修复不支持的导入组合。

## 本轮实测

环境为真实 Chrome **155.0.8059.80**、Edge **155.0.4283.45**，串行执行。四档各录制受控同步片与本地无元数据四秒音乐片，共 16 份；同步片使用 3 秒现有音频，在 1.5–1.55 秒显示白色闪帧。本地音乐不加入 fixture，不记录原文件信息。后续同步片在角落加入已有旋转元素，中心同步区域不变。

所有 16 份都实际使用所选尺寸、采集请求与码率，含一个 VP9 视频流和一个 Opus 音频流，在页面音量 0 时仍有声，FFmpeg 完整解码通过。首批 A/V 事件差最大 28ms、结尾差最大 56ms、相对源时长差最大 203ms，均在既有 100ms/250ms 门槛内。8 份音乐片的实际包帧率及最大帧间隔通过，后续 6 份同步片也通过。

**首批 720p30 同步片失败**：Chrome/Edge 分别约 25.45/27.65fps，最大视频包间隔 500/268ms。失败样本保留，不改判为 unavailable。独立浏览器首录复测在各档均复现；代表性同步片结果如下，均未达到实际包帧率 ±5% 和最多四个目标帧间隔的既有门槛：

| 档位 | Chrome 实际 fps / 最大间隔 | Edge 实际 fps / 最大间隔 |
| --- | --- | --- |
| 720p30 | 25.27 / 500ms | 27.65 / 266ms |
| 720p60 | 47.30 / 634ms | 52.01 / 417ms |
| 1080p30 | 23.93 / 633ms | 26.65 / 366ms |
| 1080p60 | 45.29 / 754ms | 48.89 / 550ms |

诊断中视觉 RAF 没有对应停顿，主线程没有对应长任务；加入持续运动、先截图呈现预览、提前一秒获取采集流均未解决。问题发生于采集/编码输出侧，具体浏览器内部原因尚未确定。无效的等待实验已撤回，生产录制顺序不变。三个可选档位因此继续排除，720p30 保留历史已接受的默认能力，但**这次发现的首录稳定性缺口未关闭**，不能宣称当前全部媒体门槛通过。没有改写 V5/V6 历史证据或生成整体 readiness。

## 复现与验证

- `tests/e2e/visualizer-output.spec.ts`：真实输出参数、录制锁/释放、页面静音音轨、导入/草稿不降档与早期拒绝。
- 默认仅测正式可用档位；可设置 `VISUALIZER_MUSIC_FILE` 指向本地 ≤8 秒片段，`VISUALIZER_OUTPUT_RUN` 指定独立 run ID。
- 候选矩阵设置 `VISUALIZER_RECORDING_TRIAL=1`。测试仅在自身 localhost 模块响应中放开静态可用性表，生产代码没有旁路；文件标记 candidate trial。失败测量保持失败，不因恢复正式门禁而改判。
- `node tests/scripts/verify-visualizer-output.mjs <run-id> --all` 要求完整 16 份矩阵；不加 `--all` 可检查子集，但每个档位仍需 Chrome/Edge × 同步/音乐四份才可汇总通过。
- 验证器以实际 packet PTS 计算平均 fps，不使用有时为 1000/1 的 WebM 名义帧率；同时检查包顺序、最大间隔、结构、尺寸、时长、音轨、同步和实际解码。

原始媒体、浏览器/采集元数据、RAF/长任务诊断和测量 JSON 仅留在忽略目录 `artifacts/visualizer-composition/output/`。`trial-1` 保存首批矩阵；`cold-60`、`cold-1080-30`、`cold-1080-60`、`preview-check` 等独立样本保留上述复现。短片结果不代表长曲性能或原生 OS 保存人工验收。

代码交付验证：类型检查、6 项录制单元测试、13 项工具测试、生产构建与仓库/文档检查通过。Chrome/Edge 共 4 项正式界面专项通过（禁用选项、导入/草稿/导出保留、预检前拒绝与手动恢复）；测试专用候选响应另在两端生成 1080p60 样本，证明正式代码无旁路。浏览器“成功生成文件”与媒体稳定性结论分别记录，不能混为全部通过。
