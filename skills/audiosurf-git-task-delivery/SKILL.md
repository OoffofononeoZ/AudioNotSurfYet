# 修改任务与本地交付

读取文档、`AGENTS.md`、`SKILL.md` 及其引用文本时，命令或 API 必须显式指定 UTF-8 编码参数；PowerShell 使用 `Get-Content -Encoding UTF8`，内容检索使用 `rg --encoding utf-8`。工具不支持时换用支持显式编码的读取方式，不能依赖默认编码或控制台设置；仅列文件名无需编码参数。

owner 已授权修改任务按小目标完成适用验证后本地提交，无需再次确认；不包含推送、部署、发布、切换分支或历史重写。

## 开始

读取 `git status --short`、当前分支和暂存区，记录本次将触及的文件及已有修改。不以 reset、checkout、批量覆盖或格式化清理工作树。Git 所有权检查失败时，确认目标是当前仓库，仅对命令使用 `git -c safe.directory=<当前仓库绝对路径>`，不设置全局或通配信任。

## 提交粒度

- 一次任务或计划包含多个小目标时，先识别各小目标的提交边界，按依赖顺序推进；每个小目标完成适用验证后及时单独提交，不能等全部小目标完成后一次性提交。
- 单一目标可以一次性提交。属于同一小目标的实现、测试及相关文档一起提交，不按文件类型机械拆分，也不为增加提交次数制造空提交。

## 完成

按[双端合同](../../docs/context/desktop.md)在每个小目标同步实际受影响的 Web/Electron 文档、命令、平台差异与验证状态；共享改动完成双端适用检查，单端修改说明影响依据。长期 Goal 更新当前阶段、完成提交、未验证项与下一步后继续推进，不等全部阶段结束才提交；桌面本地安装包不扩大为签名、推送或公开发布授权。

1. Prettier 支持的手写代码按明确的本次修改文件列表运行 `npm run format -- <file...>` 与 `npm run format:check -- <file...>`；其他代码人工正常排版。不格式化全仓、生成文件或用户无关修改，不压缩代码规避行数。再按实际改动运行适用验证，修复相关失败；不能运行的部分如实说明。
2. 修改交付时运行 `npm run skills:install`、`npm run codemap` 和 `npm run repo:check`；工具实现变化再运行 `npm run test:tools`。检查 `git diff --check`。
   手写 Markdown 超过 500 行需审阅并精简冗余文字，800 行及以上禁止提交；若精简可能丢失关键信息，保留原文并汇报，停止提交，不靠压行或跳过检查继续交付。
3. 审阅 diff，区分用户已有修改；只暂存本次文件或明确片段。审阅 `git diff --cached`、`--name-status` 和 `--check`。
4. 已有无关暂存修改时用临时索引隔离本次提交，保留用户索引；同文件混合改动无法可靠分离时说明阻碍，不一起提交。
5. 为当前已完成的小目标创建对应 feat/fix/refactor/docs/test/chore 本地提交，相关地图和发现入口随该小目标提交；有后续小目标则继续推进并分别提交。每次提交后核对短提交号、剩余状态和用户修改。

只读、无变化或仅检查任务不生成文件、不创建空提交。构建改写生成声明时保留任务前用户差异，只交付必要生成变化。大型音频、权重、模型产物及秘密配置遵守现有忽略规则，不能用 `git add .` 顺带提交。正式证据仍需真实干净实现 commit；提交本身不能证明 canonical 或 readiness 通过。
